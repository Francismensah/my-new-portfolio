Cloudflare 522 Caused by an EC2 Public IP Change

Customers reported "Service Unavailable." Investigation showed a Cloudflare 522, then an origin IP mismatch after an EC2 restart. Root cause: public IP drift. Resolution: move to a stable Elastic IP.

📅 2026 ⏱ 7 min read ✍️ Francis Morkeh Mensah
AWS Terraform Cloudflare EC2 Incident

Incident Summary

This was handled as an SRE troubleshooting incident. Customers started reporting Service Unavailable. At the edge, Cloudflare was returning 522, which means Cloudflare could not connect to the origin in time.

The application itself was not the issue. The origin mapping path was broken, so users experienced unavailability even though workloads were otherwise healthy.

What a 522 means: Cloudflare reached the edge of the network, but it could not complete the connection to the origin within the expected time. In practice, that can be a stale IP, an unreachable server, or a service that is not listening where Cloudflare expects it to be.

Troubleshooting Timeline

Investigation sequence:

  • Checked Cloudflare status and confirmed 522.
  • Validated DNS/origin mapping for the domain.
  • Compared mapped origin IP with the current EC2 public IP in AWS Console.
  • Found they were different.
  • Reviewed instance status and saw the server had restarted recently.

Root Cause

Further investigation confirmed the EC2 origin was using a regular public IP, not an Elastic IP. After restart, AWS assigned a new public IP. Cloudflare was still trying the previously mapped IP, which caused the 522 responses.

The failure chain was:

  • Instance restarted.
  • Non-EIP public IP changed.
  • Domain/origin still pointed to the old IP.
  • Users saw 522 because the origin could not be reached.

Resolution

The fix was to attach an Elastic IP to the instance so the origin IP remains stable across restarts. 

main.tfresource "aws_eip" "instance_name" {
  instance = aws_instance.instance_name.id
  domain   = "vpc"

  tags = {
    Name = var.instance_name
  }
}

After associating the EIP and updating origin mapping, Cloudflare could consistently reach the instance and the 522 errors cleared.

Why this works: an Elastic IP gives you a stable public address that you control. The instance can restart, but the origin IP stays fixed, which means DNS and reverse-proxy layers do not have to chase a moving target.

Corrective Actions

  • Replace ephemeral public IPs with Elastic IPs for internet origins.
  • Keep origin mapping tied to stable addresses only.
  • Manage EIP association through Terraform for repeatability.
  • Add restart checks to verify origin IP consistency post-reboot.

SRE Takeaway

In production troubleshooting, always verify the control plane path first: edge status, DNS/origin mapping, and current infrastructure state. In this case, customer-reported unavailability looked like an app outage but was an origin identity drift caused by restart behavior.

  • Treat stable origin addressing as a reliability requirement.
  • Use EIP or load balancers for externally reachable services.
  • Document restart side effects in incident runbooks.

Takeaway

Customers reported service unavailable. 522 confirmed edge-to-origin failure. Root cause was IP mismatch after restart because the instance used public IP instead of EIP. Moving to aws_eip removed that failure mode.
