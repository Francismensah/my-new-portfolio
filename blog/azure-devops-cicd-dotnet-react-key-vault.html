Building a Reliable CI/CD Pipeline for .NET and React with Azure DevOps

Independent delivery pipelines, environment-safe configuration, and operational guardrails for a production API and frontend.

202614 min readFrancis Morkeh Mensah
Azure DevOpsKey VaultSRECI/CD

Hero image: a clean architectural illustration showing separate .NET and React delivery paths converging on dev, staging, and production Linux hosts.

The problem: fast delivery without fragile releases

For this case study, I run an ASP.NET Core API and a React single-page application as two independently deployable services. The team needs frequent releases, but a green build alone is not enough: configuration must be environment-safe, secrets must stay out of source control, and a bad production deployment must have a short path back to the last known good version.

My goal is a pipeline that makes the safe path the easy path. Every change is tested and scanned, promotion is explicit, and runtime health—not just task completion—decides whether a release stays live.

What CI/CD means here

Continuous integration (CI) validates each change by building, testing, scanning, and packaging it into a repeatable artifact. Continuous delivery (CD) promotes that immutable artifact through environments with approvals, checks, deployment verification, and rollback. CI answers “can we release this?” CD answers “should we release this here, now, and keep it running?”

Case study architecture

The API and frontend live in separate repositories so ownership, release cadence, and rollback boundaries remain clear. Each repository has its own Azure DevOps YAML pipeline and publishes a versioned artifact. Both services run on Linux hosts: the ASP.NET Core API is a dedicated systemd unit, while the React artifact is served by Nginx, also managed as a systemd service. Azure DevOps promotes the same artifact to separate dev, staging, and production hosts.

  • Repositories: orders-api for ASP.NET Core and orders-web for React.
  • Stages: CI, dev deployment, staging deployment, and production deployment.
  • Environments: Azure DevOps environments named dev, staging, and prod, each mapped to a Linux host group with checks and approval policy.
  • Artifacts: a published .NET package and a production React bundle. CD never rebuilds source.
  • Isolation: an API change can roll forward without forcing a frontend release, and vice versa.

  C[Commit / Pull Request] --> B[Build]
  B --> T[Unit tests + coverage]
  T --> S[Dependency + secret + image scans]
  S --> A[Immutable artifact]
  A --> D[Dev]
  D --> G[Staging]
  G --> P[Production]

CI stage: prove the artifact is releasable

CI is intentionally boring. It restores from lockfiles, builds in a clean agent, runs tests, and emits one artifact. I fail fast on linting and security findings that violate the repository policy. Coverage is a signal, not a vanity target: I track changed-line coverage and require a threshold that protects critical code.

.NET API pipeline

trigger:
  branches: { include: [ main ] }

pool:
  vmImage: ubuntu-latest

variables:
  buildConfiguration: Release

stages:
- stage: CI
  jobs:
  - job: Api
    steps:
    - task: UseDotNet@2
      inputs:
        packageType: sdk
        version: 8.x
    - task: DotNetCoreCLI@2
      displayName: Restore
      inputs: { command: restore, projects: '**/*.csproj' }
    - task: DotNetCoreCLI@2
      displayName: Build
      inputs:
        command: build
        projects: '**/*.csproj'
        arguments: '--configuration $(buildConfiguration) --no-restore'
    - task: DotNetCoreCLI@2
      displayName: Test with coverage
      inputs:
        command: test
        projects: '**/*Tests/*.csproj'
        arguments: '--configuration $(buildConfiguration) --collect:"XPlat Code Coverage" --no-build'
    - task: PublishCodeCoverageResults@2
      inputs:
        summaryFileLocation: '$(Agent.TempDirectory)/**/coverage.cobertura.xml'
    - task: DotNetCoreCLI@2
      displayName: Publish artifact
      inputs:
        command: publish
        projects: '**/*.csproj'
        arguments: '--configuration $(buildConfiguration) --output $(Build.ArtifactStagingDirectory)/api --no-restore'
    - publish: '$(Build.ArtifactStagingDirectory)/api'
      artifact: api

React pipeline

trigger:
  branches: { include: [ main ] }

pool:
  vmImage: ubuntu-latest

stages:
- stage: CI
  jobs:
  - job: React
    steps:
    - task: NodeTool@0
      inputs: { versionSpec: '20.x' }
    - script: npm ci
      displayName: Install locked dependencies
    - script: npm run lint
      displayName: Lint
    - script: npm test -- --runInBand
      displayName: Unit tests
    - script: npm run build
      displayName: Production build
    - task: AzureKeyVault@2
      inputs:
        azureSubscription: 'sc-orders-nonprod'
        KeyVaultName: 'kv-orders-dev'
        SecretsFilter: 'PUBLIC_API_URL'
    - script: echo "Public config is injected at deploy; no secret is bundled"
      displayName: Validate public configuration
    - publish: '$(Build.SourcesDirectory)/dist'
      artifact: web

Both pipelines also run a dependency scan (NuGet or npm), a secret scan over source and logs, and a container image scan when the service is containerized. A scan must publish actionable results and fail on the agreed severity, rather than becoming a dashboard nobody checks.

Configuration and secrets with Azure Key Vault

Credentials, connection strings, signing keys, and tokens never belong in Git, pipeline YAML, screenshots, or task output. A repository is copied, forked, cached, and inspected by more people than the production runtime. Pipeline variables are also easy to echo accidentally. I keep only non-sensitive defaults and references in source.

I provision one Key Vault per environment—kv-orders-dev, kv-orders-staging, and kv-orders-prod—with identical secret names. That convention lets code and templates stay consistent while values and access boundaries differ. The pipeline service connection uses a managed identity or workload identity federation, never a long-lived client secret, and receives only get and list permissions for the required vault.

For pipeline-time values, I use AzureKeyVault@2 or a Key Vault-linked variable group. Secrets are marked secret and are not passed to scripts unless needed. For runtime values, the Linux host's managed identity reads Key Vault directly. In Program.cs, the API uses the Azure SDK credential chain:

using Azure.Identity;

var builder = WebApplication.CreateBuilder(args);

builder.Configuration.AddAzureKeyVault(
    new Uri(builder.Configuration["KeyVault:Uri"]!),
    new DefaultAzureCredential());

var app = builder.Build();
app.MapHealthChecks("/health");
app.Run();

The package is Azure.Extensions.AspNetCore.Configuration.Secrets. DefaultAzureCredential uses developer credentials locally and the VM or host managed identity in Azure, without changing application code between environments. React is different: anything in its bundle is public. I inject only public, non-sensitive configuration such as an API base URL at deploy time through a runtime config file or server-side template. No database password or private token belongs in a browser bundle.

Key Vault is configured with soft delete, purge protection, diagnostic logging, and alerts for unusual access. I rotate secrets on a schedule and after incidents, test that applications reload or restart safely, and record who accessed which vault. Rotation is an operational workflow, not a one-time provisioning task.

CD stage: promote the same artifact to systemd services

CD downloads the CI artifact and deploys it unchanged to Linux hosts. Each stage maps to an Azure DevOps environment. The environment owns approvals, branch restrictions, business-hour checks, and required health gates; these controls should not be hidden in a script that can be bypassed.

The deployment agent connects through a restricted SSH service connection. It copies the API package into a versioned directory, writes environment-specific configuration outside the artifact, updates the systemd unit's release path, runs systemctl daemon-reload, and restarts the unit. For React, it extracts the bundle into a versioned Nginx directory, atomically updates the document-root symlink, and runs systemctl reload nginx. The deploy account can operate only the approved units; it is not a general-purpose root login.

stages:
- stage: Dev
  jobs:
  - deployment: DeployDev
    environment: dev
    strategy:
      runOnce:
        deploy:
          steps:
          - download: current
            artifact: api
          - task: AzureKeyVault@2
            inputs:
              azureSubscription: 'sc-orders-nonprod'
              KeyVaultName: 'kv-orders-dev'
              SecretsFilter: 'KeyVault__Uri'
          - task: CopyFilesOverSSH@0
            inputs:
              sshEndpoint: 'ssh-orders-dev'
              sourceFolder: '$(Pipeline.Workspace)/api'
              targetFolder: '/srv/orders-api/releases/$(Build.BuildId)'
          - task: SSH@0
            inputs:
              sshEndpoint: 'ssh-orders-dev'
              runOptions: inline
              inline: |
                sudo systemctl daemon-reload
                sudo systemctl restart orders-api
                curl --fail --retry 10 http://127.0.0.1:8080/health

- stage: Staging
  dependsOn: Dev
  condition: succeeded()
  jobs:
  - deployment: DeployStaging
    environment: staging
    strategy:
      runOnce:
        deploy:
          steps:
          - download: current
            artifact: api
          - task: CopyFilesOverSSH@0
            inputs:
              sshEndpoint: 'ssh-orders-staging'
              sourceFolder: '$(Pipeline.Workspace)/api'
              targetFolder: '/srv/orders-api/releases/$(Build.BuildId)'
          - task: SSH@0
            inputs:
              sshEndpoint: 'ssh-orders-staging'
              runOptions: inline
              inline: 'sudo systemctl restart orders-api && curl --fail http://127.0.0.1:8080/health'

- stage: Production
  dependsOn: Staging
  condition: succeeded()
  jobs:
  - deployment: DeployProduction
    environment: prod
    strategy:
      runOnce:
        deploy:
          steps:
          - download: current
            artifact: api
          - task: CopyFilesOverSSH@0
            inputs:
              sshEndpoint: 'ssh-orders-prod'
              sourceFolder: '$(Pipeline.Workspace)/api'
              targetFolder: '/srv/orders-api/releases/$(Build.BuildId)'
          - task: SSH@0
            inputs:
              sshEndpoint: 'ssh-orders-prod'
              runOptions: inline
              inline: 'sudo systemctl restart orders-api && curl --fail http://127.0.0.1:8080/health'

In the real template, each environment has its own SSH service connection, Key Vault reference, host group, systemd unit name, and post-deployment smoke test. The React pipeline uses the same promotion model but updates the Nginx document-root symlink and reloads nginx.service. Production requires approval plus checks for change window, artifact provenance, and staging success.

# React deploy steps run on the same environment stages
- task: CopyFilesOverSSH@0
  inputs:
    sshEndpoint: 'ssh-orders-prod'
    sourceFolder: '$(Pipeline.Workspace)/web'
    targetFolder: '/srv/orders-web/releases/$(Build.BuildId)'
- task: SSH@0
  inputs:
    sshEndpoint: 'ssh-orders-prod'
    runOptions: inline
    inline: |
      sudo ln -sfn /srv/orders-web/releases/$(Build.BuildId) /srv/orders-web/current
      sudo systemctl reload nginx
      curl --fail --retry 10 https://orders.example.com/

Define the failure boundary

Every stage needs a clear answer to “what happens when this step fails?” A failed build blocks the artifact. A failed dev smoke test blocks staging. A failed staging check blocks production. A failed production health check stops traffic or swaps the slot back. This sounds obvious, but it prevents a common anti-pattern: a pipeline reports partial failure while a later task continues and publishes a misleading success signal.

I also separate deployment errors from application errors. A permission failure, package upload timeout, or unavailable agent should retry within safe limits and page the pipeline owner. A 500 response after deployment should stop promotion and trigger rollback. The distinction improves incident routing: platform teams investigate delivery mechanics while service owners investigate application behavior.

Choose a deployment strategy deliberately

Rolling deployments replace hosts or restart instances gradually and are a good default for backward-compatible API changes. Blue/green runs two versioned directories or host groups, validates the inactive systemd unit, and switches traffic through Nginx or a load balancer. Canary sends a small percentage of traffic to a new host group and is best for high-risk changes where real production telemetry matters. App Service deployment slots are not part of this design; the equivalent control is versioned systemd units, separate host groups, or an upstream traffic switch.

flowchart LR
  R[Release]
  R --> RO[Rolling: replace instances gradually]
  R --> BG[Blue/green: validate slot, swap traffic]
  R --> CA[Canary: route small traffic percentage]
  RO --> D1[Lower cost, slower rollback]
  BG --> D2[Fast rollback, extra capacity]
  CA --> D3[Best signal, routing complexity]

Reliability practices I keep in the pipeline

  • Health checks: expose readiness and liveness separately; test dependencies without making a database outage look like a deploy failure.
  • Smoke tests: call a safe API endpoint and load the React shell after every deployment.
  • Rollback: retain the previous artifact and make rollback a pipeline action, not an emergency rebuild.
  • Feature flags: decouple code deployment from risky behavior changes and turn off a feature without redeploying.
  • Speed: cache NuGet and npm packages with Azure Pipelines caching, but key caches by lockfile hash.
  • Metrics: track deployment frequency, lead time for changes, change failure rate, and mean time to restore. These DORA metrics reveal whether speed is creating operational debt.

Make the pipeline observable

A pipeline is production infrastructure for the delivery system, so I instrument it like a service. Each run has a correlation ID, commit SHA, artifact version, approver, target environment, and deployment result. Logs are retained long enough to investigate a failed release, but sensitive task output is filtered before retention. Azure DevOps run summaries link to the systemd journal, Application Insights traces, and the rollback runbook.

Alerts should be actionable. I alert when a release fails repeatedly, when a production smoke test fails, or when deployment lead time crosses its normal range. I do not alert on every transient package download retry. The objective is to protect the release path and shorten diagnosis, not create another noisy monitoring surface.

Standardize the boring parts

Reusable YAML templates keep security and release controls consistent across repositories. I centralize the scan steps, artifact naming, test-result publishing, systemd deployment, and rollback task, then pass only service-specific values such as project paths, host groups, and unit names. Pull requests can review a small service template instead of a different home-grown pipeline in every repository. When the platform team updates an approved task version or a policy threshold, the change is visible and can be rolled out deliberately rather than copied manually.

Common mistakes

  • Configuration drift: use the same secret names, systemd unit templates, and infrastructure-as-code across environments; vary values, not structure.
  • Secrets in logs: never print all variables, command lines, or generated config files. Masking is a backstop, not a design.
  • Over-permissioned connections: scope service connections to one subscription or resource group and Key Vault roles to the exact operations required.
  • No rollback plan: rehearse a release symlink reversal and systemd restart, and confirm the previous artifact is retained before the first incident.
  • Slow pipelines: parallelize independent jobs, cache dependencies, and run the smallest useful test set on pull requests while keeping the full suite on main.

A production failure caught before customers noticed

In one release, the API package copied successfully but the systemd unit entered a restart loop because a new startup dependency was unavailable. The deployment task was green—the files were present—but the post-deployment health check and systemctl is-active --quiet orders-api failed within seconds. The pipeline stopped promotion, repointed the release symlink to the previous version, restarted the unit, and opened an incident notification with the failed check and artifact ID.

The important control was not the rollback command. It was treating application health as part of deployment success. We fixed the dependency timeout, added a staging test for the failure mode, and kept the release process unchanged for the next deploy.

Conclusion

  1. Build and release the .NET API and React frontend independently as immutable, tested artifacts.
  2. Use one Key Vault per environment, least-privilege identity, and runtime retrieval so secrets never enter source or browser bundles.
  3. Make health checks, approvals, rollback, and delivery metrics first-class parts of CD.
