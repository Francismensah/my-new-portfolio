Migrating My Portfolio from EC2 to Cloudflare Workers (and the 126 MiB File That Almost Stopped Me)

A static site does not need a server just because it started on one. Here is how I moved my portfolio off EC2, and why a successful build still ended in a failed deployment.

📅 2026 ⏱ 10 min read ✍️ Francis Morkeh Mensah
Cloudflare Workers Deployment SRE

Why I moved from EC2

My portfolio at infrabyfrancis.me is a static site: HTML, CSS, JavaScript, images, and blog pages. For a while, it lived on an EC2 instance behind Nginx, with Cloudflare in front for DNS and caching.

That setup worked, but it was a lot of infrastructure for a site that did not need a server. There was no dynamic backend, no database, and no long-running process to keep alive. I was paying the operational tax of running and patching a machine just to serve files that could be delivered from the edge.

The goal was simple: remove EC2 from the serving path and deploy the site directly to Cloudflare Workers.

The architecture before the move

GitHub
   ↓
EC2
   ↓
Nginx
   ↓
Cloudflare
   ↓
infrabyfrancis.me

GitHub held the source, EC2 ran Nginx, and Cloudflare sat in front as the edge and DNS layer. EC2 was effectively a file server with extra steps.

Preparing the Cloudflare deployment

The repository already had a small Node build script that generates the blog listings from articles.json: 

npm run build

# runs
node scripts/build.mjs

The Cloudflare build environment picked up Node.js 24.18.0 and npm 10.9.2. Dependencies installed successfully with npm clean-install --progress=false, and the build output was exactly what I expected: 

Built blog listings: 10 published, 7 home previews

That was the first useful checkpoint. The source could build in the new environment. The deployment failure came later.

The 126 MiB deployment failure

Wrangler auto-detected the project as a static Worker and chose the repository root as the output directory: 

Worker Name: my-new-portfolio
Framework: Static
Output Directory: .

In practical terms, Wrangler was treating the entire repository as the static asset directory. That included the generated website, but also the dependencies and scripts used to build it.

Eventually the asset scan reached this file:

node_modules/workerd/bin/workerd

The binary was 126 MiB. Cloudflare Workers allows individual static assets up to 25 MiB, so the deployment stopped with an asset-too-large error.

The important distinction: the build succeeded. The asset scan failed. Those are separate stages with separate failure modes, and a green build did not mean the site was ready to ship.

Finding the root cause

The clue was in the Wrangler output: Output Directory: .. Because the output directory was the repository root, Wrangler was scanning everything under it, including node_modules.

The website only needed these files and directories at runtime:

index.html
blog/
assets/
images/
articles.json

It did not need the following to serve a page:

node_modules/
scripts/
package.json
package-lock.json
.git/
.wrangler/
*.md

Those are build-time inputs and repository metadata, not deployment assets. Wrangler could not infer that distinction from a repository root on its own.

The .assetsignore fix

I added a .assetsignore file at the repository root:

node_modules
.git
.wrangler
scripts
package.json
package-lock.json
*.md

The file serves the same purpose for Wrangler's asset upload that .gitignore serves for Git. It defines what should not be included in the static asset set.

The repository structure did not need to change. Cloudflare still had access to the source, scripts, and dependencies during the build. The ignore file only stopped Wrangler from trying to publish build-time material as part of the website.

Deployment succeeded

The build command remained the same and produced the same result:

Executing user build command: npm run build

> build
> node scripts/build.mjs

Built blog listings: 10 published, 7 home previews

Success: Build command completed

Wrangler still reported the repository root as the output directory, but .assetsignore filtered the upload down to the files that mattered: 

Found 27 new or modified static assets to upload.
Uploaded 27 files
Success: Deploy command completed

The asset list now looked like a website rather than a development environment: 

/index.html
/blog/index.html
/blog/cloudflare-522-ec2-public-ip-change.html
/blog/nginx-502-fix.html
/assets/home.css
/assets/base.css
/assets/site.js
/images/SLO.png
/images/systemd.jpeg
/articles.json
Build dependencies are not deployment assets. The same repository can contain everything needed to generate a site and only a small subset of what should be served publicly.

Moving the custom domain

Cloudflare provided default Worker hostnames for production and previews. I wanted the public URL to remain infrabyfrancis.me, so I pointed the existing custom domain at the Worker instead.

After confirming that the custom domain served the site correctly, I disabled the default workers.dev URL. The public identity of the portfolio stayed the same; only the compute and delivery path changed underneath it.

The architecture after the move

GitHub
   │
   ▼
Cloudflare Build
   │
   ├── npm clean-install
   │
   ├── npm run build
   │      │
   │      └── scripts/build.mjs
   │
   ▼
Wrangler
   │
   ├── assets directory = .
   └── .assetsignore
   │
   ▼
Cloudflare Worker
   │
   ▼
Custom Domain
   │
   ▼
Static Portfolio

Compared with the original setup, there is no EC2 instance to patch, no Nginx configuration to maintain, and no server to pay for simply serving static files.

What I learned

The lesson I keep coming back to is that a successful build does not necessarily mean a successful deployment. Build, asset scanning, and deployment are separate stages, so each needs its own success check. 

Before the fix:
Build:       SUCCESS
Asset scan:  FAILURE
Deployment:  FAILURE

After the fix:
Build:       SUCCESS
Asset scan:  SUCCESS
Deployment:  SUCCESS

The broader lesson is about boundaries. Build dependencies, build scripts, generated static files, and deployment assets are different categories. When a deploy tool uses the repository root as its output directory, that boundary must be made explicit.

Practical takeaway

If your deployment output directory is the repository root, assume the deploy tool can see everything in that root. Use an explicit ignore file such as .assetsignore to separate what the build needs from what the edge should serve.
