Kubernetes for SREs: What You Actually Need to Know

Production troubleshooting, error cause-and-effect patterns, and real debugging workflows for fintech and ecommerce systems.

📅 2026 ⏱ 22 min read ✍️ Francis Morkeh Mensah
Kubernetes Debugging SRE Production DevOps

Introduction: The Kubernetes Gotchas Nobody Warns You About

Kubernetes tutorials show you how to deploy a pod. Production shows you how things break at 3 AM in ways the docs never mentioned.

This isn't an introduction to Kubernetes. It's a runbook for the errors that will bite you in production. If you've been paged about CrashLoopBackOff, OOMKilled, or mysterious Pending pods, this is for you.

Most of these scenarios come from production systems handling millions in daily transactions (fintech) or serving millions of concurrent shoppers (ecommerce). The debugging patterns are universal.

What Makes Kubernetes Fail in Production

Kubernetes failures generally fall into 5 categories that require different debugging approaches:

  • Pod Lifecycle Issues: Application crashes, memory exhaustion, scheduler can't place the pod.
  • Networking: Services unreachable, DNS failures, egress blocked by policy.
  • Storage: Volumes won't mount, permissions errors, access mode conflicts.
  • Configuration: Missing secrets/configmaps, invalid image references.
  • Resource Constraints: Quota exhaustion, HPA misconfiguration, node pressure.

1. Pod Lifecycle & Scheduling Errors

CrashLoopBackOff: Your First Real Kubernetes War Wound

This is the most common error in production. The pod keeps restarting in a loop. Each restart attempt backs off exponentially (1s, 2s, 4s, 8s, etc.) until it gives up and waits 5 minutes.

Real Scenario: Payment Processing Pod Crashes in Production

Situation: Your fintech platform's payment processor pod enters CrashLoopBackOff at 2 PM. Transactions are backing up. You have 10 minutes to fix it.

Your Investigation:

$ kubectl get pods -n payment NAME READY STATUS RESTARTS AGE payment-proc-xyz 0/1 CrashLoopBackOff 12 8m $ kubectl describe pod payment-proc-xyz -n payment Last State: Terminated Reason: ExitCode 1 Message: Started: Wed, 24 May 09:12:30 +0000 Finished: Wed, 24 May 09:12:35 +0000 Events: Type Reason Age Message ---- ------ ---- ------- Warning BackOff 2m Back-off restarting failed container $ kubectl logs payment-proc-xyz -n payment --previous panic: failed to connect to database: connection refused goroutine 1 [running]: main.main() /app/payment/main.go:42 +0x1234
🔴 Cause

The pod starts but can't connect to its database. The application panics after 5 seconds. kubelet restarts it.

  • DB secret not mounted
  • DB host DNS unresolvable
  • DB service down/restarting
  • Network policy blocks egress
  • Auth credentials wrong
✅ Solution

Check the pod's environment and previous logs to identify the root cause before restarting.

  • kubectl logs --previous (you only have a few seconds of logs before it crashes)
  • kubectl exec (only if it reaches ready state)
  • kubectl describe pod (shows pod events/errors)
  • Test connectivity from a debug pod
Pro Tip: Debug Pod for Network Testing

When your app crashes due to connection errors, use a debug pod to test from within the cluster:

$ kubectl run -it --rm debug --image=ubuntu --restart=Never -n payment -- bash root@debug:/# apt-get update && apt-get install -y dnsutils postgresql-client root@debug:/# nslookup postgres.payment.svc.cluster.local Server: 10.0.0.10 Address: 10.0.0.10#53 Name: postgres.payment.svc.cluster.local Address: 10.0.0.52 root@debug:/# psql -h postgres.payment.svc.cluster.local -U admin -d paymentdb -c "SELECT 1;" SSL connection (protocol: TLSv1.3, cipher: TLS_AES_256_GCM_SHA384, bits: 256, compression: off) (1 row)

If nslookup fails, CoreDNS is broken. If psql fails, firewall or credentials are wrong.

Lesson: CrashLoopBackOff is never a Kubernetes problem—it's an application configuration problem. Your app is starting but failing immediately. Always check --previous logs first. Never restart the pod; fix the root cause.

OOMKilled: Running Out of Memory in Production

The Linux kernel's Out-of-Memory killer terminates the process. The pod is evicted. New pod spins up. Same pod dies. This looks similar to CrashLoopBackOff but is more insidious.

Real Scenario: Ecommerce Checkout Service Memory Leak

Situation: During a flash sale, your ecommerce checkout pods get OOMKilled every 10 minutes. The pod is requested to use 512Mi but keeps exceeding it.

$ kubectl describe pod checkout-abc123 -n ecommerce State: Waiting (reason:CrashLoopBackOff) Last State: Terminated Reason: OOMKilled Exit Code: 137 Limits: memory: 512Mi Events: Warning OOMKilled 1m The container was OOMKilled $ kubectl top pod checkout-abc123 -n ecommerce --containers POD NAME CONTAINER CPU(cores) MEMORY(bytes) checkout-abc123 checkout 10m 510Mi $ kubectl logs checkout-abc123 -n ecommerce --tail=50 [1:M 24 May 12:15:00.000] * Ready to accept connections [1:M 24 May 12:15:15.001] * User connected: order:xyz [1:M 24 May 12:15:30.002] * Memory allocated: 100MB [1:M 24 May 12:16:00.003] * Memory allocated: 200MB [1:M 24 May 12:16:30.004] * Memory allocated: 300MB ... (continues until 512MB) [1:M 24 May 12:17:00.005] * Out of memory, terminating
🔴 Cause

Memory usage is growing over time. This is a memory leak. The pod is holding onto objects it should have released.

  • Connection pools not shrinking
  • Cache growing unbounded
  • Goroutine/thread leak
  • Large JSON responses accumulating
  • Buffer reuse not happening
✅ Solution

Immediate: Increase the memory limit and request temporarily. Permanent: Profile the pod and find the leak.

  • Increase resources.limits.memory to 1Gi as a band-aid
  • Add memory profiling (pprof for Go, -XX:+PrintGCDetails for Java)
  • Set resources.requests to match actual usage
  • Run load tests locally to reproduce and debug
Incident Postmortem Note: Flash sales spike memory usage 10x. Requests and limits were tuned for average load. Add HPA based on memory metrics and set requests correctly to prevent node eviction of other pods.

Pending: Pod Stuck Waiting for Resources

The scheduler can't find a node to run the pod. It waits indefinitely in the Pending state. This is often caused by resource constraints or node affinity rules.

Real Scenario: Database Migration Pod Can't Schedule

Situation: You deploy a database migration job that requests 4 CPUs and 8Gi memory. All nodes are at capacity from regular services. The migration pod stays Pending.

$ kubectl get pods -n db-migration NAME READY STATUS RESTARTS AGE migration-xyz 0/1 Pending 0 15m $ kubectl describe pod migration-xyz -n db-migration Status: Pending Events: Type Reason Age Message ---- ------ ---- ------- Warning FailedScheduling 15m 0/5 nodes are available: 5 Insufficient cpu $ kubectl top nodes NAME CPU(cores) CPU% MEMORY(Mi) MEMORY% node-1 3.9 95% 6200Mi 95% node-2 3.85 94% 6050Mi 93% node-3 3.92 96% 6100Mi 94% node-4 3.88 95% 6010Mi 92% node-5 3.9 95% 6150Mi 94%
🔴 Cause

The cluster is fully utilized. No node has 4 contiguous CPUs available. The scheduler refuses to place the pod.

  • Over-provisioning resource requests
  • No node selector → pod goes anywhere
  • Taint/toleration mismatch
  • Node affinity too strict
✅ Solution

Don't scale down critical services. Reduce the migration job's request, or add temporary nodes.

  • Reduce resources.requests.cpu to 2 CPU for migration
  • Add a preemption policy: other pods get evicted
  • Run migration in a separate cluster
  • Use a node pool with less memory-intensive workloads
Pro Tip: Check Node Allocatable vs. Used

Nodes have overhead (kubelet, system pods). See what's actually available:

$ kubectl describe nodes node-1 Capacity: cpu: 4 memory: 8Gi Allocatable: cpu: 3.8 memory: 7.5Gi Allocated resources: (Total limits may exceed 100 percent, if individual containers exceed their limit.) Resource Requests Limits -------- -------- ------ cpu 3.75 3.8 memory 7.2Gi 7.5Gi (No unallocated resources detected)

Allocatable is what's actually available for your workloads. Requests consume from it.

ImagePullBackOff: Wrong Image or Registry Issues

kubelet tries to pull the image but can't. Reasons vary: wrong tag, private registry credentials missing, registry unreachable.

Real Scenario: Deployment Rollout with Wrong ECR Image Tag

Situation: You deploy a new version of your payment API but reference the wrong ECR image tag. The old pod is still running (v1.5), but the new deployment tries to pull v2.0-typo.

$ kubectl describe pod payment-api-new-xyz -n payment Events: Type Reason Age Message ---- ------ ---- ------- Normal Scheduled 5m Successfully assigned to node-1 Normal BackOff 2m (x3 over 5m) Back-off pulling image Warning Failed 2m (x3 over 5m) Failed to pull image Warning Failed 2m (x3 over 5m) Error response from daemon: pull access denied $ kubectl logs payment-api-new-xyz -n payment Error from server (BadRequest): container "payment-api" in pod "payment-api-new-xyz" is waiting to be started: image can't be pulled $ aws ecr describe-images --repository-name payment-api --region us-east-1 IMAGE DETAILS imageTag: ["v1.5", "v1.4", "v1.3", "latest"] imagePushedAt: 2026-05-24 (No v2.0-typo tag found!)
Debugging Checklist:
  • Is the tag actually in the registry?
  • Is the registry reachable from the node?
  • Does the node have credentials? (ImagePullSecrets for private registries)
  • Is the image name spelled correctly? (typos, wrong region, wrong account)

2. Networking: The Invisible Killer

Service Not Reachable: Connection Refused or Timeout

You have a service. A pod tries to connect to it. Nothing happens. No error. Just silence. This is networking.

Real Scenario: Ecommerce: Cart Service Can't Talk to Inventory

Situation: Cart service tries to call the inventory service: inventory.ecommerce.svc.cluster.local:8080. Timeouts. Cart operations hang. Customers can't check out.

$ kubectl get svc -n ecommerce NAME TYPE CLUSTER-IP EXTERNAL-IP PORT(S) cart ClusterIP 10.0.100.50 8080/TCP inventory ClusterIP 10.0.100.75 8080/TCP $ kubectl get endpoints -n ecommerce inventory NAME ENDPOINTS AGE inventory 5m (No endpoints! Pods are not being added to the service) $ kubectl get pods -n ecommerce -l app=inventory NAME READY STATUS RESTARTS AGE inventory-abc-1 0/1 CrashLoopBackOff 12 20m inventory-abc-2 0/1 CrashLoopBackOff 12 20m inventory-abc-3 0/1 CrashLoopBackOff 12 20m (Ah! The pods aren't ready. That's why no endpoints.) $ kubectl logs inventory-abc-1 -n ecommerce --previous error: failed to connect to database: timeout connecting to mysql.ecommerce.svc.cluster.local:3306 (Now we're getting somewhere! The inventory pods can't connect to their DB.)
🔴 Cause

Service exists but has no healthy pods to route to. Kube-proxy won't route traffic to unhealthy pods.

  • Backend pods are in CrashLoopBackOff
  • Pod readiness probes are failing
  • Selector doesn't match pod labels
  • Namespace mismatch
✅ Solution

Debug the backend pods first. Fix the root cause before debugging the service.

  • kubectl get endpoints svc-name shows actual targets
  • Check pod labels match the service selector: kubectl describe svc
  • Check readiness probes: kubectl get pod -o jsonpath=...
  • Fix the pod issue (usually connectivity or config)
Pro Tip: Verify Service Routing
$ kubectl get svc inventory -n ecommerce -o jsonpath='{.spec.selector}' map[app:inventory] $ kubectl get pods -n ecommerce -L app NAME APP inventory-abc-1 inventory (Labels match. But are the pods ready?) $ kubectl get pods -n ecommerce inventory-abc-1 -o jsonpath='{.status.conditions[?(@.type=="Ready")]}' {"lastTransitionTime":"2026-05-24T12:10:00Z","lastUpdateTime":"2026-05-24T12:15:00Z", "message":"Readiness probe failed: HTTP probe failed with statuscode: 503","reason":"Failure","status":"False","type":"Ready"} (Readiness probe is failing! That's why it's not in endpoints.)

CoreDNS: When Service Names Disappear

Pods can't resolve svc.cluster.local names. They're trying to reach 10.0.0.x ClusterIPs but DNS isn't responding.

Real Scenario: CoreDNS Pod Evicted During Node Pressure

Situation: A spike in memory usage causes the node to evict pods. CoreDNS pods (which run on most nodes) get evicted. DNS stops working. Everything times out.

$ kubectl get pods -n kube-system -l k8s-app=kube-dns NAME READY STATUS RESTARTS AGE coredns-5d78c0854b-xyz1 0/1 Pending 0 8m coredns-5d78c0854b-xyz2 0/1 Pending 0 8m (Both CoreDNS pods are Pending!) $ kubectl describe nodes | grep MemoryPressure MemoryPressure False DiskPressure False PIDPressure False (Maybe check why pods are pending...) $ kubectl describe pod coredns-5d78c0854b-xyz1 -n kube-system Events: Warning FailedScheduling 8m 0/3 nodes are available: 3 nodes are tainted with node-role.master:NoSchedule (CoreDNS has a nodeAffinity that's too strict!) $ kubectl scale deployment coredns --replicas=1 -n kube-system deployment.apps/coredns scaled $ kubectl get pod -n kube-system -l k8s-app=kube-dns NAME READY STATUS RESTARTS AGE coredns-5d78c0854b-xyz1 1/1 Running 0 2m
Lesson: CoreDNS is not special. It can fail like any other pod. If it's evicted, DNS breaks everywhere. Monitor CoreDNS pod count and set strict QoS for it.

Ingress 502/504: Backend Not Ready or Timeout

The ingress is routing traffic correctly, but the backend services return 502 (Bad Gateway) or 504 (Timeout). This usually means the pods aren't healthy.

Real Scenario: Fintech Payment Portal Returns 502 After Deployment

Situation: You deploy a new version of the payment portal. The ingress starts returning 502s. The pod is running but not ready.

$ curl -v https://payments.fintech.com/api/check HTTP/2 502 Content-Length: 0 $ kubectl get pods -n payment-portal NAME READY STATUS RESTARTS AGE portal-deployment-1 0/1 Running 0 2m (Pod is Running but not Ready. That's the problem.) $ kubectl describe pod portal-deployment-1 -n payment-portal Readiness: http-get http://:8080/healthz port 8080, delay=10s, timeout=5s, period=10s ... (details of readiness probe config) Last Probe: Wed, 24 May 12:30:00 +0000 Probe Failed (exit code 1): HTTP probe failed with statuscode: 503 (Readiness probe is failing. Ingress won't route to it.) $ kubectl exec portal-deployment-1 -n payment-portal -- curl -v http://localhost:8080/healthz HTTP/1.1 503 Service Unavailable X-Error: Cannot connect to config database (App is running but its dependencies aren't ready yet.) $ kubectl logs portal-deployment-1 -n payment-portal | head -20 2026-05-24 12:25:00 [INFO] Starting application 2026-05-24 12:25:01 [INFO] Connecting to postgres://config-db.payment-portal.svc.cluster.local:5432 2026-05-24 12:25:05 [ERROR] Connection timeout after 4s: no response from database 2026-05-24 12:25:05 [ERROR] Readiness checks failing (Config database isn't reachable from the portal pod.)
🔴 Cause

Pod is running but readiness probe fails. Ingress routes only to Ready pods. No Ready pods = 502.

  • App dependencies not ready
  • Readiness probe timeout too short
  • Database migrations not complete
  • Slow app startup
✅ Solution

Fix the readiness probe or its timeout. Or ensure dependencies start first.

  • Increase initialDelaySeconds to 30s (give app time to start)
  • Increase timeoutSeconds to 10s (give check time to complete)
  • Use init containers to wait for dependencies
  • Check app logs for startup errors
Fix Applied: Updated readiness probe delay to 30s and timeout to 10s. Portal reached Ready state. Ingress started routing. 502 errors stopped. Incident resolved in 3 minutes.

3. Storage: The Persistent Data Trap

PVC Stuck in Pending: StorageClass or Provisioner Issues

You claim a PersistentVolume (PV) but it's stuck in Pending. The storage provisioner either doesn't exist or is broken.

Real Scenario: Database Cluster Can't Start: Storage Provisioner Down

Situation: You spin up a Postgres cluster using Helm. The PVCs for data and WAL logs are Pending. The pods are also Pending.

$ kubectl get pvc -n databases NAME STATUS VOLUME CAPACITY ACCESS MODES STORAGECLASS AGE postgres-data-0 Pending gp3 10m postgres-wal-0 Pending gp3 10m $ kubectl describe pvc postgres-data-0 -n databases Events: Type Reason Age Message ---- ------ ---- ------- Warning ProvisioningFailed 5m (x7 over 10m) failed to provision volume with StorageClass "gp3": rpc error: code = Unavailable desc = EBS provisioner unavailable (The EBS provisioner is down or misconfigured!) $ kubectl get pods -n ebs-csi-driver NAME READY STATUS RESTARTS AGE ebs-csi-controller-0 1/2 CrashLoopBackOff 15 2h ebs-csi-node-xyzab 2/2 Running 0 2h ebs-csi-node-abcde 2/2 Running 0 2h (Controller is in CrashLoopBackOff!) $ kubectl logs -n ebs-csi-driver ebs-csi-controller-0 -c ebs-plugin failed to mount /var/run/secrets/kubernetes.io/serviceaccount: permission denied (RBAC issue! Service account doesn't have permission to describe snapshots.)
Debugging Checklist:
  • Does the StorageClass exist?
  • Is the provisioner (EBS CSI, GCE PD, Ceph, etc.) running and healthy?
  • Does the provisioner have RBAC permissions?
  • Are cloud provider credentials configured?
  • Check provisioner logs for errors

Volume Mount Errors: Reference Wrong Secret/ConfigMap

You reference a secret or configmap in a volume that doesn't exist. The pod fails to mount it and enters CreateContainerConfigError.

Real Scenario: Application Config Volume References Wrong Secret

Situation: Your deployment mounts a secret app-secrets that doesn't exist in the namespace. Pods can't start.

$ kubectl describe pod app-xyz -n production Status: Waiting Reason: CreateContainerConfigError Message: can't find secret "app-secrets" Events: Warning FailedMountSecretVolume 5m Unable to mount volumes for pod "app-xyz": "app-secrets" not found $ kubectl get secrets -n production NAME TYPE DATA AGE app-secret Opaque 3 20m (Typo! It's "app-secret", not "app-secrets") $ kubectl patch deployment app -n production --type merge -p '{"spec":{"template":{"spec":{"volumes":[{"name":"config","secret":{"secretName":"app-secret"}}]}}}}' deployment.apps/app patched $ kubectl get pods -n production -l app=app --field-selector=status.phase=Running NAME READY STATUS RESTARTS AGE app-new-abc 1/1 Running 0 30s
Pro Tip: Validate Manifest Before Deploying
$ kubectl apply -f deployment.yaml --dry-run=client -o yaml # This validates the manifest without applying it

ReadWriteOnce Conflict: Two Pods on Different Nodes

Two pods on different nodes try to mount the same PVC with RWO (ReadWriteOnce) access mode. Only one node can mount it. The second pod's mounting fails.

Real Scenario: StatefulSet Database Replica Can't Mount PVC

Situation: You have a 3-node cluster. A MySQL StatefulSet with 2 replicas tries to mount. Pod-0 is on node-1 (works). Pod-1 tries to attach to node-2 but gets blocked by RWO.

$ kubectl get pvc -n databases NAME STATUS VOLUME CAPACITY ACCESS MODES mysql-data-0 Bound pv-mysql-0 50Gi RWO mysql-data-1 Pending RWO (PVC for replica-1 is Pending!) $ kubectl describe pvc mysql-data-1 -n databases Type Reason Age Message Warning FailedAttachVolume 5m AttachVolume.Attach failed for volume "pv-mysql-0": "pv-mysql-0" is already in use at node-1 (Same PV can't be attached to node-2 with RWO!) $ kubectl edit storageclass gp3 # Change allowVolumeExpansion and other settings # Solution: Each replica needs its own PV (not shared)
Lesson: RWO means one node at a time. For multi-node databases, use:
  • Separate PVs for each replica (replication handles sync)
  • RWX (ReadWriteMany) if the storage backend supports it (NFS, CephFS)
  • Don't try to share a single RWO PVC across multiple pods on different nodes

4. Configuration & Secrets

CreateContainerConfigError: Missing ConfigMap or Secret

Pod tries to use a ConfigMap or Secret that doesn't exist in the namespace.

Debugging Pattern

$ kubectl describe pod failing-pod -n production Status: Waiting (reason:CreateContainerConfigError) Message: can't find secret "db-password" $ kubectl get secrets -n production | grep password (No matches) $ # Check if secret exists in wrong namespace $ kubectl get secrets -n default | grep password db-password Opaque 1 10m $ # Copy the secret to the right namespace or fix the pod spec $ kubectl get secret db-password -n default -o yaml | kubectl apply -f - -n production

5. Resource Constraints & Quotas

Forbidden: Exceeded Quota

You try to deploy a pod but hit a namespace ResourceQuota. The quota is exhausted.

Real Scenario: Fintech: Canary Deployment Blocked by Quota

Situation: You're rolling out a canary deployment that requests 2 CPUs and 2Gi memory. The namespace quota is exhausted.

$ kubectl apply -f canary-deployment.yaml -n payment-prod Error from server (Forbidden): error when creating "canary-deployment.yaml": pods "canary-abc" is forbidden: exceeded quota: requests.cpu (requested: "2", used: "18", limited: "20"), requests.memory (requested: "2Gi", used: "18Gi", limited: "20Gi") $ kubectl describe resourcequota -n payment-prod Name: prod-quota Namespace: payment-prod Resource Used Hard -------- ---- ---- pods 45 50 requests.cpu 18 20 requests.memory 18Gi 20Gi limits.cpu 40 50 limits.memory 36Gi 50Gi (CPU and memory requests are exhausted!) $ # Option 1: Reduce canary resource requests $ kubectl edit deployment canary -n payment-prod # Change requests.cpu from 2 to 1, requests.memory from 2Gi to 1Gi $ # Option 2: Increase the quota $ kubectl edit resourcequota prod-quota -n payment-prod # Change limits to requests.cpu: 30, requests.memory: 30Gi $ kubectl apply -f canary-deployment.yaml -n payment-prod deployment.apps/canary created
Pro Tip: Set Reasonable Defaults

Use LimitRange to prevent runaway requests:

apiVersion: v1 kind: LimitRange metadata: name: resource-limits namespace: payment-prod spec: limits: - max: cpu: 2 memory: 2Gi min: cpu: 100m memory: 128Mi default: cpu: 500m memory: 512Mi defaultRequest: cpu: 250m memory: 256Mi type: Container

HPA Not Scaling: Metrics Not Available

Your HorizontalPodAutoscaler is stuck at 1 replica. It's not scaling up even when CPU is high. Usually, metrics-server isn't installed or the pod doesn't have resource requests.

Real Scenario: Ecommerce: Flash Sale Traffic Not Triggering HPA

Situation: A flash sale starts. Traffic spikes to 5x normal. Your HPA has a target CPU of 70%. But pods aren't scaling up.

$ kubectl describe hpa checkout -n ecommerce Status: unknown (metrics not available yet) Current Replicas: 1 Desired Replicas: 1 Metrics: resource name current average target average ---- ------- ------ cpu 70% (Metrics not available!) $ kubectl get pod checkout-xyz -n ecommerce -o jsonpath='{.spec.containers[0].resources}' {"limits":{"cpu":"1","memory":"512Mi"}} (No requests! HPA needs requests to calculate percentage. It uses: current CPU / requested CPU) $ # Fix: Add requests to deployment $ kubectl set resources deployment checkout -n ecommerce \ --requests=cpu=250m,memory=256Mi \ --limits=cpu=1,memory=512Mi $ # Wait for metrics to populate (30-60s) $ kubectl describe hpa checkout -n ecommerce Current Replicas: 1 Desired Replicas: 4 Metrics: resource name current average target average ---- ------- ------ cpu 350m (140%) 175m (70%)
Result: HPA scaling kicked in. Pods increased from 1 to 4. Load balanced. Checkout latency dropped from 5s to 500ms. Flash sale succeeded.

6. Node Issues: When Infrastructure Breaks

NodeNotReady: Kubelet Stopped Reporting

A node is in NotReady state. kubelet crashed or stopped reporting heartbeats. All pods on that node are stuck or evicted.

Real Scenario: EC2 Instance Kernel Panic

Situation: One of your 5 nodes enters NotReady. Pods are being evicted. The node's kubelet isn't responding.

$ kubectl get nodes NAME STATUS ROLES AGE VERSION node-1 Ready worker 120d v1.28.0 node-2 NotReady worker 120d v1.28.0 node-3 Ready worker 120d v1.28.0 node-4 Ready worker 120d v1.28.0 node-5 Ready worker 120d v1.28.0 $ kubectl describe node node-2 Status: NotReady Conditions: Type Status LastHeartbeatTime Message Ready False Wed, 24 May 09:00:00 +0000 Kubelet stopped posting node status. $ # SSH to the node and check kubelet status $ ssh ubuntu@node-2.internal $ sudo systemctl status kubelet ● kubelet.service - Kubelet Loaded: loaded (/lib/systemd/system/kubelet.service; enabled) Active: inactive (dead) since Wed 2026-05-24 09:00:00 UTC ... (Kubelet is dead!) $ sudo journalctl -u kubelet -n 50 -e May 24 08:59:30 node-2 kernel: [12345.123456] Out of memory: Kill process 1234 (container) score 800 (Kernel OOM killer killed the container!) $ sudo systemctl restart kubelet $ sudo systemctl status kubelet ● kubelet.service - Kubelet Loaded: loaded (/lib/systemd/system/kubelet.service; enabled) Active: active (running) $ kubectl get nodes NAME STATUS ROLES AGE VERSION node-2 Ready worker 120d v1.28.0
Why This Happened: A single pod was misconfigured with no memory limits. It grew unbounded, consumed all node memory, kernel OOM-killed it, and kubelet crashed trying to handle the eviction.

DiskPressure / MemoryPressure: Node Under Resource Stress

A node has DiskPressure or MemoryPressure. kubelet evicts pods to free resources.

$ kubectl describe nodes node-1 Conditions: MemoryPressure True ... Kubelet has MemoryPressure DiskPressure False ... Ready True ... $ kubectl get pods -n production -o json | \ jq '.items[] | select(.status.reason=="Evicted") | .metadata.name' cache-pod-1 cache-pod-2 cache-pod-3 (Pods are being evicted from node-1!) $ # Solution: Identify the culprit $ kubectl top pod --all-namespaces --sort-by=memory NAMESPACE POD NAME CPU(cores) MEMORY(bytes) production analytics-worker-1 100m 7Gi production cache-redis-1 50m 2Gi logging fluentd-xyz 10m 800Mi (analytics-worker is using 7Gi! That's probably too much.) $ # Check if limits are set $ kubectl describe pod analytics-worker-1 -n production | grep -A 5 Limits Limits: cpu: 2 memory: 8Gi (Limits are set to 8Gi, but actual usage is 7Gi. The node only has 8Gi total available!) $ # Fix: Reduce the pod's resources or add memory to the node $ kubectl set resources deployment analytics-worker -n production \ --limits=memory=4Gi --requests=memory=2Gi

7. Rollout & Deployment Issues

Deployment Stuck: Readiness Probes Never Pass

You roll out a new deployment. It spins up new pods but they never reach Ready state. The old ReplicaSet stays up. No progress.

Real Scenario: Fintech: Payment Service Rollout Hangs

Situation: You deploy a new version of the payment service. The new ReplicaSet is created but pods are stuck at 0/1 Ready. The old version is still serving traffic. Rollout is blocked.

$ kubectl rollout status deployment payment-service -n payment Waiting for rollout to finish: 1 old replicas, 1 new replicas, 1 updated replicas not ready... (Hangs here indefinitely) $ kubectl get replicasets -n payment NAME DESIRED CURRENT READY AGE payment-service-v1-xyz123 1 1 1 10m payment-service-v2-abc456 1 1 0 2m (v1 is Ready. v2 is not.) $ kubectl describe pod payment-service-v2-abc456-pod1 -n payment Conditions: Initialized True Ready False ContainersReady True (Container is ready but overall pod is not. This is rare. Quick Reference: SRE Debugging Flowchart

When you get paged about a Kubernetes issue, follow this order:

  • 1. Pod Status: kubectl get pods -n namespace — Is it Running/Pending/Failed?
  • 2. Pod Description: kubectl describe pod name — What does the event log say?
  • 3. Logs: kubectl logs name --previous — Why did it crash?
  • 4. Service/Endpoints: kubectl get endpoints svc — Is traffic routing?
  • 5. Node Health: kubectl describe nodes — Is the node NotReady?
  • 6. Resources: kubectl top pods/nodes — OOMKilled? Running out of CPU?
  • 7. Quotas: kubectl describe resourcequota — Hit a limit?

Closing: The Pattern Behind the Chaos

Most Kubernetes issues boil down to a few patterns:

  • Configuration mismatch: Wrong selector, missing secret, wrong namespace.
  • Resource constraints: Pod too big for node, OOM, quota exhausted.
  • Dependency failures: Database down, service unreachable, CoreDNS broken.
  • Timing issues: Readiness probe too strict/fast, initialization incomplete.
  • Infrastructure problems: Node not ready, kubelet crashed, storage provisioner down.

When debugging, work backward from the symptom. If pods aren't ready, check their logs. If logs aren't available, check pod description. If the pod is pending, check node capacity. If nodes are full, check if any pod is hoarding memory.

The key: each error tells you exactly where to look next. Learn to read the error messages and you'll fix 90% of incidents in under 5 minutes.
