How I Finally Built and Deployed My Personal Portfolio

This project sat in my notes for over a year. Here is how I finally shipped it to production using AWS EC2, Nginx, Cloudflare, and Certbot.

2026 10 min read Francis Morkeh Mensah
AWS EC2 Nginx Cloudflare Certbot Linux

From "I should build this" to "it is live"

I had been planning this portfolio since last year. I had the ideas, rough notes, even a few half-finished designs, but I kept pushing it aside for client work, incidents, and everything else that feels urgent in day-to-day engineering.

At some point, I realized I was helping teams ship reliable systems for everyone else while my own public profile stayed unfinished. So I blocked time, treated it like a real production project, and decided to ship it end to end.

I wanted this build to reflect how I actually work as an SRE and DevOps engineer: simple architecture, explicit configs, observable behavior, and predictable deployment steps.

Tech Stack I Used

  • AWS EC2 for compute hosting
  • Nginx as the web server and reverse proxy layer
  • Git and GitHub for source control and delivery workflow
  • Cloudflare for DNS management and domain mapping
  • Certbot + Let's Encrypt for SSL/TLS certificates
  • Linux (Amazon Linux 2023) for server administration and hardening

Source code stack

  • Language: HTML5 for structure and page content
  • Language: CSS3 for styling, layout, and theme variables
  • Language: Vanilla JavaScript (ES6) for interactivity
  • Framework: none (intentionally built without React/Vue/Angular)
  • Libraries/services: Google Fonts (IBM Plex Mono, Fraunces, DM Sans) and inline SVG assets for icons/visuals

Deployment Walkthrough

Below is the exact flow I followed to move from local files to a public HTTPS website.

Since this server runs Amazon Linux 2023, I used yum commands throughout (on AL2023, yum is the compatibility wrapper over dnf).

1) Launching an EC2 instance

I provisioned an Amazon Linux 2023 EC2 instance in AWS, attached a security group, and allowed only the minimum ports needed:

  • 22 for SSH access
  • 80 for HTTP
  • 443 for HTTPS

I also allocated an Elastic IP so the server address stays stable. That avoids DNS churn later and makes the setup more predictable.

2) Cloning the project from Git

Once I SSHed into the server, I updated packages and pulled the site source directly from GitHub. 

sudo yum update -y
sudo yum install -y git

cd ~
git clone https://github.com//.git

I like this flow because deployment state is tied to commit history. It is easy to audit what changed and when.

3) Moving the project to /var/www/<project-name>

I moved the static site files into the standard web root location and fixed permissions so Nginx could serve them. 

sudo mkdir -p /var/www/portfolio
sudo rsync -av --delete ~/<your-portfolio-repo>/ /var/www/portfolio/

      sudo chown -R nginx:nginx /var/www/portfolio
sudo chmod -R 755 /var/www/portfolio

Using rsync made updates clean and repeatable while keeping directory structure intact.

4) Installing and configuring Nginx

Next, I installed Nginx and created a dedicated server block for the domain instead of modifying the default config. 

sudo yum install -y nginx
sudo systemctl enable --now nginx

      sudo vim /etc/nginx/conf.d/portfolio.conf
server {
    listen 80;
    server_name infrabyfrancis.me www.infrabyfrancis.me;

    root /var/www/portfolio;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}

sudo nginx -t
sudo systemctl reload nginx

I always run nginx -t before reload. That simple habit prevents avoidable downtime.

5) Setting up the domain

I had already registered the domain, so the next job was linking it to the EC2 instance IP. I prepared both the apex domain and www so users can access either variant.

6) Configuring DNS and domain mapping with Cloudflare

I pointed Cloudflare DNS records to my Elastic IP and turned on proxy mode for edge protection and performance. 

Type: A
Name: @
Content: <EC2-Elastic-IP>
Proxy status: Proxied

Type: CNAME
Name: www
Content: infrabyfrancis.me
Proxy status: Proxied

After propagation, the domain resolved correctly and traffic started reaching Nginx as expected.

7) Securing the site with SSL using Certbot

With HTTP working end to end, I added TLS and automatic certificate renewal using Certbot. 

sudo yum install -y certbot python3-certbot-nginx
sudo certbot --nginx -d infrabyfrancis.me -d www.infrabyfrancis.me

Certbot updated the Nginx config to redirect HTTP to HTTPS and issued trusted certificates from Let's Encrypt. 

sudo certbot renew --dry-run

I run the dry-run renewal test immediately so I know future renewals will not surprise me.

Challenges and lessons learned

The hardest part was not technical complexity, it was consistency. Starting was easy. Finishing and polishing was the real challenge.

A few practical lessons stood out:

  • Treat personal projects like production systems and they actually get shipped.
  • Keep deployment steps explicit and documented, even for "small" static sites.
  • Validate every change in sequence: DNS, Nginx config, SSL, then redirects.
  • Simplicity wins. A clean static architecture is easier to maintain, secure, and troubleshoot.
Operationally, this build reminded me that reliability starts with small habits: test configs before reload, lock down ports, and automate anything repetitive.

What is next

Right now, deployment is still semi-manual. It works, but it is not the end state I want.

My next step is setting up a full GitHub Actions CI/CD pipeline so that every push to the main branch can run checks and deploy automatically to EC2. The goal is to eliminate manual deployment drift and make releases repeatable.

Once that is in place, this portfolio will not just describe my engineering style, it will run on the same discipline: automated, observable, and reliable by design.

Final takeaway

I had been planning this site since last year. Shipping it reminded me that momentum matters more than perfect timing. Build, deploy, learn, iterate.
