Fixing the Nginx 502 Bad Gateway — upstream sent too big header

Users couldn't log in across multiple internal services. No code had changed. The fix was four lines of Nginx config.

📅 2025 ⏱ 8 min read ✍️ Francis Morkeh Mensah
Nginx SRE Production Incident DevOps

Overview

Authentication failures started appearing across several internal services simultaneously. Users attempting to log in were met with a blank page or an error screen. No application code had changed. No deployments had gone out. The infrastructure hadn't been touched.

Checking the Nginx error logs told the story immediately:

nginx error.log
upstream sent too big header while reading response header from upstream

This is a classic reverse proxy misconfiguration — one that's easy to miss until your headers grow large enough to trigger it.

Root Cause

Nginx acts as a reverse proxy, sitting between the client (browser) and the upstream application server. When the upstream returns a response, Nginx reads the headers into an internal memory buffer before forwarding to the client.

By default, these buffers are intentionally small — designed for the era of simple HTTP responses with minimal headers. Modern web applications are a different beast. They often return:

  • Large JWT tokens or OAuth tokens set as cookies
  • Multiple session cookies from authentication providers
  • Feature flag headers from A/B testing frameworks
  • Verbose security headers (CSP, CORS, HSTS policies)
  • Multiple Set-Cookie directives from SSO systems

When the combined size of these headers exceeds Nginx's proxy buffer, Nginx fails — returning a 502 Bad Gateway to the client.

Nginx Default Buffer Limits

To understand why this happens, it helps to know what Nginx's defaults actually are:

Directive Default What It Controls
proxy_buffer_size 4k / 8k Buffer for the first part of the response (headers)
proxy_buffers 8 × 4k/8k Number and size of buffers for the response body
proxy_busy_buffers_size 8k / 16k Max size of buffers busy sending to the client
proxy_max_temp_file_size 1024m Max size of temp file when buffers are full
💡 Note: proxy_buffer_size specifically handles the response header. At 4–8 KB, a single large JWT cookie can exceed this limit.

The Fix

The solution is to increase the proxy buffer sizes in the location / block of each affected server block, and to disable temp file offloading — which can introduce disk I/O under load.

Configuration Change

nginx.conf / site config# Inside the relevant server block
server {
    ...

    location / {
        proxy_pass  http://upstream_service;

        # Increased buffer sizes to handle large response headers
        proxy_buffer_size        128k;
        proxy_buffers            4 256k;
        proxy_busy_buffers_size  256k;
        proxy_max_temp_file_size 0;
    }
}

What Each Directive Does

Directive Old New Reason
proxy_buffer_size 8k 128k Handles large response headers including auth tokens
proxy_buffers 8 × 4k 4 × 256k 1MB total buffer capacity for response bodies
proxy_busy_buffers_size 16k 256k More data in-flight to the client at once
proxy_max_temp_file_size 1024m 0 (off) Eliminates disk I/O fallback; keep in memory
⚠️ On proxy_max_temp_file_size 0: Setting this to 0 disables disk spilling entirely. Appropriate when upstream responses fit in your configured buffers. If you serve large file downloads, consider leaving temp files enabled and only increasing proxy_buffer_size.

Applying the Change Safely

Always validate your Nginx config before reloading. A syntax error will take down your server. 

$ sudo nginx -t
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful

$ sudo systemctl reload nginx

Using reload instead of restart is important — it performs a graceful reload that finishes in-flight requests with zero downtime.

Prevention & Best Practices

  • Set sensible buffer defaults globally — Add proxy buffer sizes to your base Nginx template so all new server blocks inherit them.
  • Monitor header sizes — Periodically inspect auth-heavy response headers with curl -I or log $upstream_http_* variables.
  • Scope changes to affected locations — Apply increased buffers only to location / blocks that need them. Don't waste memory on static asset endpoints.
  • Keep auth tokens lean — Audit what's in your cookies and JWT claims. Large tokens with redundant data are often the upstream root cause.
  • Alert on 502 spike rates — A sudden increase in Nginx 502s is often the first signal of buffer exhaustion. Set thresholds before users notice.

💡 Key Engineering Takeaway

Not every 502 is an application crash. Nginx's default proxy buffer sizes were designed for a simpler era of HTTP. As authentication systems have grown more sophisticated — SSO, JWTs, OAuth — response headers have grown with them. Infrastructure defaults need to keep pace. A four-line config change resolved a production incident that looked, on the surface, like a broken login system.
